# 技能启用/关闭：耗时分析与优化选择

日期：2026-10-30，Asia/Shanghai。范围：调研与测试，不实施优化。

## 结论

主要问题不是技能描述、头像或页面数据太大，而是一次操作串行执行了两项重工作：先启动 CLI 全量检测 Agent，再启动 CLI 修改关联并同步。第二项在临时环境里也要十几秒。原生页面不需要每次启动 CLI，并且会立即改变按钮外观、合并连续点击，因此“看起来很快”和“实际同步已经完成”需要分开判断。

建议先做方案 A + B：去掉重复检测，改善等待反馈和连续操作；如果要求真正接近原生的完成速度，再推进方案 C 的正式授权常驻接口。单改缓存不能解决所有等待。

## 1. 实测结果和边界

本机 CLI 版本为 `magpie 0.1.2169`。测试时插件的 `resolveMagpieExecutable()` 选择了 `E:\magpie.com`；它是本机的 Windows 命令行入口。测试运行时为 Bun 1.3.9，Magpie 的插件宿主使用 Bun 1.4.4。

真实资源库当前有 28 个技能、3 个原生项目；本轮检测得到 16 个可管理的 Windows Agent。

| 测试 | 耗时 | 可以说明什么 |
| --- | ---: | --- |
| 真实环境 `magpie ls`，两次新 CLI 进程 | 13,396 / 12,758 ms | 每次强制检测本身已足够造成明显等待 |
| 当前服务逻辑：请求保持原关联不变 | 12,772 ms | 即使无需写入，也先支付检测成本 |
| 同一请求，仅用测试替身让 discovery 使用现有 15 秒缓存 | 8 ms | 命中缓存可以去掉这次额外等待，不代表真实开关也只需 8 ms |
| 真实数据 `buildState()`，30 次 | 平均 5.36 ms，最大 7.29 ms | 读取资源库、描述及生成页面数据不是当前主要瓶颈 |
| `magpie --version`，单次 | 587 ms | 启动程序并输出简单信息并不天然需要十几秒 |
| 临时配置，无社区插件：`ls` | 11,701 ms | 社区插件加载并不是全部原因 |
| 临时配置，无社区插件：启用 / 关闭 / 再启用一个小技能 | 13,010 / 12,707 / 15,571 ms | 很小的数据集也存在较重的 CLI 操作成本 |
| 同类临时配置，复制公共插件代码但不复制登录态：`ls` | 17,226 ms | 插件环境会影响冷启动成本 |
| 同类临时配置，有公共插件：启用 / 关闭 / 再启用 | 16,837 / 15,468 / 19,764 ms | 每次写入启动 CLI 的成本也值得优化 |

测试方法：

- 真实环境只测试读取和“不改变现有状态”的请求。`setAgents`、同步及宿主操作替身在被调用时直接报错，确保无法借此写入真实资源库。
- 服务请求通过 `Request -> service.fetch` 在进程内执行，不包含浏览器渲染或真实 HTTP 传输。请求前先让初次检测完成，避免把首次加载混入点击数据。
- 真正的启用/关闭只发生在临时 HOME、配置、Agent 目录中。验证了临时 `library.json` 的关联结果及 Codex 技能链接的目标。
- 两组临时环境只使用一个很小的测试技能；公共插件组复制公共包代码，不复制供应商密钥、登录态或真实项目。它们不是实际用户环境的完整复制。
- 真实 `library.json` 在测试前后 SHA-256 一致。没有修改插件业务源码。
- 现有相关测试 11 项通过，涵盖隐藏关联保留、不可管理 Agent 拒绝写入、权限和资源库读取。这些测试大多使用替身，不会暴露真实 CLI 的十几秒成本。

限制：样本数少，不能当作稳定的 p95；未计量原生 WebView 本次真实点击到后台完成的时间，未分离 Windows 文件检查、安装检测、供应商读取各自的 CPU/等待占比。因此不能断言所有十几秒都来自某个具体子函数，也不能宣称原生真实同步已实测为毫秒级。

## 2. 当前插件为什么慢

### 2.1 点击前强制全量检测

`lib/service.mjs:640` 的 `mutateAssociation()` 在写队列内先调用：

```js
await discovery.refresh({ force: true });
```

`lib/discovery.mjs` 已有 15 秒缓存和进行中的请求合并，但 `force: true` 跳过新鲜缓存。`lib/cli.mjs` 的 `discoverAgents()` 实际运行 `magpie ls`。

`ls` 不只是返回安装状态。上游 `internal/cli/main.go` 的 `list()` 还读取各 Agent 的配置字段、模型等信息。本插件只需要是否安装和是否支持技能，却支付了更广泛读取的成本。

即使最终发现关联集合没有变化，`sameSet()` 也在这次检测之后才执行。因此无变化请求仍等待约 12.8 秒。

项目技能操作也有同类检测，位于 `lib/service.mjs:484`；但本次主测是全局资源库技能的 Agent 开关，项目同步不能直接套用全部结论。

### 2.2 真正写入再启动一次 CLI

关联有变化时，`lib/service.mjs:676` 调用 `setAgents()`；`lib/cli.mjs` 再通过 `Bun.spawn()` 执行：

```text
magpie library skill agents <技能> <完整 Agent 列表>
```

新 CLI 进程无法直接继承原生常驻进程的内存缓存。上游 CLI 在到达技能写入前还有启动流程，并逐个校验传入的 Agent。实际写入则仍走 Magpie 的统一资源库同步。

上游 `Library.sync()` 枚举目标 Agent，并处理指令、MCP、hooks、子 Agent、技能副本编辑、技能分发和项目技能等步骤。这里只切换一个技能，但不等于同步步骤只检查这一个技能。

临时环境的一个小技能也要 12.7～19.8 秒，说明不能只优化页面来解决后台完成速度。无社区插件仍慢，又说明“关闭其他插件”不是完整解法。

### 2.3 页面等待方式进一步放大体验差异

`page/app.js:1607` 的单 Agent 操作：

- 先设置单个全局 `busySkill`。
- 等请求返回后才替换关联状态，没有预先显示用户想要的选中状态。
- 操作开始、返回及结束均涉及全页面重绘。
- `if (state.busySkill) return` 会阻止等待期间的其他技能操作；其他卡片未必看起来被禁用，点击却不会排入待处理列表。

服务端还有全局写队列，标签、项目和关联操作共享。串行写入本身有必要，不能为了快简单地并行多个 CLI 修改同一资源库；应优化排队和合并方式。

## 3. 与 Magpie 原生管理的真实差异

本轮实际访问了官方插件文档和上游源码；关键源码固定到提交 `0414bbeddbfc2028508b610fd1e7c194143454a0`。它们是上游实现证据，不等于对本机二进制逐函数做过验证。

| 环节 | 当前插件 | 原生资源库 |
| --- | --- | --- |
| 点击前 | 强制启动 `ls` 全量检测 | Agent 列表来自已加载的页面状态 |
| 写入入口 | 启动新 CLI 进程 | 页面请求常驻 Magpie 的 `/api/library/skills/agents` |
| 实际关联函数 | CLI 最终调用 `library.SkillAgents()` | 原生 HTTP handler 调用同一函数 |
| 同步机制 | Magpie 统一同步 | 同一机制，不是只改按钮或特殊直写 |
| 查找缓存 | 每个新 CLI 重新建立进程内缓存 | 常驻进程可复用缓存；例如 `proc/look.go` 按路径目录状态保留工具查找结果 |
| 点击反馈 | 等待请求完成后才改变选中状态 | `chipsChange()` 立即改变该行按钮外观和 `aria-pressed` |
| 连续点击 | `busySkill` 期间直接返回 | 按技能维护 `writing`、`want`，等待期间更新最终意图；相同意图不重复发送 |
| 写后确认 | 重新读关联并验证，再构造页面状态 | handler 返回更新后的资源库视图及同步结果 |

所以有两种差距：后台入口造成的真实耗时差距，以及原生“先反馈、再完成”造成的感知差距。不能把原生按钮瞬间亮起当作同步已经完成的证据。

CLI stderr 还两次出现 P21 服务 `127.0.0.1:3487` 已占用的加载报错：新 CLI 加载插件时会尝试启动另一个技能服务。这是应独立处理的生命周期问题，可能带来额外工作及日志噪声；但无插件临时环境仍慢，不能把端口冲突认定为唯一根因，也不能据此认定现有页面服务已坏。

## 4. 可行方案比较

### 方案 A：保留 CLI，先去掉点击前的重复检测

做法：正常点击使用仍新鲜的检测结果；首次加载、缓存过期或手动刷新才重新检测。保持“检测失败不写入”，继续读取最新关联、保留隐藏关联、由 Magpie 写入并复核结果。

收益：在本轮条件下，新鲜缓存命中的请求可少等待约 12.8 秒。没有实际变化的请求尤其受益。已有缓存机制可复用，不需要引入新依赖。

限制：缓存过期的点击仍可能等待；真正写入还要启动 CLI，不能保证接近原生速度。若增加后台刷新，它只能把等待提前，不能减少检测总量，应避免页面隐藏时频繁扫描。

安全边界：缓存会引入最多约 15 秒的安装状态延迟。Magpie CLI 的技能适配校验仍须保留；它不应被笼统视作对所有桌面/非 CLI Agent 的“当前已安装”完整复核。若必须严格保证刚卸载便立即不可启用，需增加目标 Agent 的轻量复核，而不是只删掉 `force`。

改动量：小。优先级：最高。

### 方案 B：即时局部反馈 + 合并连续操作

做法：借鉴原生 `chipsChange()`，立即显示用户想要的状态，同时明确标注“正在应用”；只更新相关卡片。按技能保存待处理意图，短时间连续点击只提交最终结果，不再默默丢弃点击。

收益：立即改善等待体验；多次快速操作同一技能时，可以减少实际 CLI 调用次数。单次写入的后台耗时不会因此消失。

安全边界：保留全局实际写入串行；出队时重新读取关联并应用增删意图，不拿旧完整列表覆盖新状态。只有后台复核完成后才能显示“已完成”。失败恢复真实状态；旧响应不能覆盖较新的点击意图。

同一技能连续多次开关应合并，但不要未经说明就把不同技能或不同项目的操作混在一起。批量改多个技能目前不能凭空假设存在相应公开 CLI 命令。

改动量：小到中。优先级：与 A 配合。

### 方案 C：正式授权的常驻技能接口

做法：推动 Magpie 提供窄权限的技能读写桥或常驻服务接口，让 P21 的受保护服务调用现有资源库能力，不再为每次点击启动完整 CLI。接口最好接收“对某 Agent 启用/关闭”的增删意图，并在同一个权威写入进程中处理。

收益：最接近原生后台速度的方向；可避免新进程启动、重新建立工具查找缓存及重复插件初始化。同一进程中的权威锁也更适合处理原生页面与插件同时写入。

限制：本轮访问的官方页面接口只公开 `usage:summary` 和 `providers:list` 等窄读取，没有已验证的 Skills 写接口。原生私有 HTTP 路径的存在，不代表第三方页面已获得调用权限。

不得把读取主窗口凭证、绕过页面限制或直接调用私有 API 当作当前可用方案。需要上游正式授权支持；若选择自行维护 Magpie 改版，也必须先获 Ivy 同意，不能擅自替换本机程序。

改动量：中到大，并有上游依赖。优先级：要求进一步缩短真实完成时间时推进。

### 方案 D：从 Magpie 侧提供轻量 CLI 或增量同步

做法：向上游提出两项独立改进：安装状态专用的轻量读取；技能关联命令跳过无关启动工作，或让同步只重新检查受影响部分。

收益：即使不增加页面写权限，也有机会降低后台耗时；还可惠及其他 CLI 使用者。

限制：不能假设只改一个技能就只处理一个目录。共享技能目录、副本编辑回流、Applied 所有权、备份、隐藏目标和项目技能都要回归测试。单纯少扫一些目标容易改变行为。

改动量：中到大。优先级：在进一步分段计时确认热点后再考虑，不建议作为第一步。

## 5. 不建议的捷径

- 直接编辑真实 `library.json` 后调用 sync，或自行创建/删除技能链接：违反项目写入边界，也容易破坏所有权、备份和共享目录规则。
- 为省时间关闭其他插件或改变系统/安全软件设置：无插件也慢；目前没有足够证据支持这些环境改动。
- 把 `Bun.spawn()` 换成 PowerShell、`execFile()`，或只提前解析可执行文件路径：仍然是新 CLI 进程，不能保留 Magpie 的进程内缓存。
- 并行执行多个关联写 CLI：当前 CLI 使用完整 Agent 列表，多写者可能互相覆盖；插件队列不等于跨进程的权威锁。
- 等待更久、增大超时或只换加载动画：没有消除任何后台工作。单 Agent 写入当前已经有 45 秒检测和 90 秒写入超时预算。
- 先缓存头像、描述或大幅重构前端：可以以后优化，但本次页面数据构造约 5 ms，收益远小于十几秒的 CLI 等待。

## 6. 推荐顺序和验收

先实施 A + B，分别验证真实耗时和等待体验，不承诺“所有开关毫秒完成”。若实际写入仍无法接受，再评估 C；D 先进一步分段计时，不直接重写同步。

建议验收：

1. 新鲜缓存下的普通点击不额外运行 `ls`；无变化请求不运行写命令。检测过期、失败及手动刷新行为明确。
2. 点击立即显示目标状态与待完成提示；等待中其他操作不会默默丢失。相反操作合并正确。
3. 保留隐藏关联、Windows 范围和权限检查；原生页面与插件同时改变状态时不声称跨进程原子性。
4. 连续点击、失败、超时、旧响应及原生外部修改都测试；最终以 Magpie 确认的真实关联为准。
5. 在授权测试环境中增加浏览器端计时，分别记录“点击反馈”“请求返回”“实际技能分发确认”；原生与插件用相同技能、Agent、冷热条件各测多次。
