# 技能开关方案对照测试

日期：2026-10-31 至 2026-11-01，Asia/Shanghai。

## 结论

在当前 Windows 隔离环境中，A＋B 是符合现有边界的推荐组合：

- 点击后首次可见反馈的中位数约 0.30 秒。
- 后台实际完成的中位数约 2.49 秒。
- 相比当前基线，后台完成平均少约 56.5%。

A 单独实施能减少重复检测，但写入 CLI 的耗时仍有明显波动。B 不缩短后台写入，
主要解决“点击后看起来没反应”和连续点击被忽略的问题。

C 的常驻辅助程序后台完成最快，中位数约 0.93 秒，比 A＋B 再少约 1.5 秒；
但它已经在同一测试体系中复现跨进程写入丢失关联，所以本轮仍不推荐接入。

## 对照口径

实验使用本机 Magpie `0.1.2405`、当前工作区插件代码和独立临时配置。每次场景都使用
三技能、Windows Agent 测试替身，并保留一个未安装 Agent 的历史关联。
真实 Magpie 配置、真实资源库和插件源码没有切换或修改。

| 方案 | 测试路径 |
| --- | --- |
| 当前基线 | 每次操作强制 `magpie ls`，等待成功后更新页面 |
| A：缓存检测 | 使用现有 15 秒发现缓存；关联写入仍走 Magpie CLI |
| B：即时反馈 | 保留基线后端；临时页面版本先显示目标状态，并将短时间连续点击合并 |
| A＋B | 使用发现缓存，同时启用即时反馈和连续点击合并 |
| C：常驻辅助程序 | 复用固定开源提交的原生 `library.SkillAgents()`，无每次 CLI 启动；页面使用 B |

“后台完成”定义为页面收到技能关联修改响应；“首次反馈”定义为目标 Agent 按钮
显示用户想要的状态。浏览器测试每次只切换一个 Agent，中位数来自三次单次操作。

自动浏览器需要在按钮变化后轮询 DOM，故 B/C 的约 0.30 秒是包含自动化读取开销的
上界，不是逐帧精度；它仍与基线约 5.76 秒形成数量级差异。

## 浏览器计时

| 方案 | 首次反馈中位数 | 后台完成中位数 | 后台完成平均 | 相对基线平均减少 |
| --- | ---: | ---: | ---: | ---: |
| 当前基线 | 5,763 ms | 5,769 ms | 5,651 ms | 基线 |
| A：缓存检测 | 4,537 ms | 4,542 ms | 4,226 ms | 25.2% |
| B：即时反馈 | 280 ms | 4,446 ms | 4,495 ms | 20.5%* |
| A＋B | 296 ms | 2,489 ms | 2,460 ms | 56.5% |
| C：常驻辅助程序 | 297 ms | 928 ms | 1,060 ms | 81.3% |

\* B 不改变后端路径，其完成时间的表面下降属于本次样本波动，不能当作 B 的提速收益。

更可靠的判断：

- A 去掉了点击时重复发现，但 CLI 写入耗时波动较大，单次收益不稳定。
- B 将首次反馈从秒级降到自动化测得上界约 0.30 秒，后台完成不变。
- A＋B 同时改善反馈和完成时间；完成时间仍取决于 Magpie CLI。
- C 的反馈与 A＋B 相当，后台比 A＋B 中位数再少约 1.56 秒，但存在数据安全阻塞。

底层服务记录中，A 的三次关联修改均没有再次启动发现；当前基线的关联修改则都在
回复前执行了发现。

## 连续点击

实测为同一次点击目标快速切换“关闭→开启”：

| 方案 | 第二次操作 | 最终状态 | 实际关联请求 |
| --- | --- | --- | ---: |
| 当前基线 | 按钮已禁用，第二次不可用 | 仍需等待第一次完成 | 1 |
| B | 可点击，合并为初始状态 | 正确恢复 | 0 |
| A＋B | 可点击，合并为初始状态 | 正确恢复 | 0 |
| C | 双击可合并为初始状态 | 正确恢复 | 0 |

B 的实验实现使用 120 ms 短批次和每 Agent 意图合并。最终写入仍有服务端串行队列，
不把不同项目、不同 Agent 的写操作擅自合并为一次完整列表覆盖。

## C 的阻塞问题

上一轮使用原生 `edit.Filtered()` 构造合法的写入交错，复现：

1. 辅助程序修改 alpha。
2. 原生 CLI 修改 beta 并成功返回。
3. 辅助程序继续完成也返回成功。
4. beta 的关联最终被覆盖为空。

原生资源库锁是进程内互斥锁。独立辅助程序再快，也不能与 Magpie 原生进程共享
那把锁。该风险与本轮提速数据相互独立，不能用“平均快 1.5 秒”抵消。

详细证据见 [常驻辅助程序实验](sidecar-probe-2026-10-31.md)。

## 方案判断

### 推荐：A＋B

适合当前“不修改 Magpie 本体”的边界。实际写仍由 Magpie CLI 完成，保留现有
兼容性和所有权规则；改动集中在发现缓存、页面即时反馈、请求合并和测试。

仍需处理：

- 15 秒缓存到期后的重新检测。
- 检测失败时禁止写入。
- 页面隐藏时避免无意义的后台扫描。
- 连续点击相反操作时，以最终真实结果为准。
- 失败、超时和外部同时写入后的界面回滚。

### 暂不推荐：C

除非能获得 Magpie 进程级共享锁或正式常驻写入接口，否则不应因为速度更快而采用。
自行在插件侧增加普通文件锁也不能自动让原生进程遵守同一锁，不能视为完整修复。

### 排除：修改 Magpie 核心

按 Ivy 的明确限制，不修改 Magpie 本体；因此不把核心增量同步改造列为实施项。
